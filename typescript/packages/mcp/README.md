# @apso/mcp

Expose NestJS routes as MCP tools with a decorator.

A tool is a route. When an agent calls a tool, `@apso/mcp` sends the request through your app's own HTTP pipeline in memory, with the caller's headers. Your guards, pipes and filters run exactly as they do for a REST caller, so authentication, permissions and tenant scoping live in one place.

## Use

Mark the routes you want agents to call:

```ts
import { McpTool } from '@apso/mcp';

@Controller('invoice-actions')
export class InvoiceActionsController {
  @Post(':id/approve')
  @McpTool({ name: 'approve_invoice', description: 'Approve an invoice and record a note.' })
  approve(@Param('id') id: string, @Body() dto: ApproveDto) {
    // ...
  }
}
```

Serve them, after you build the OpenAPI document and before the app starts:

```ts
import { mountMcp } from '@apso/mcp';

const document = SwaggerModule.createDocument(app, options);
mountMcp(app, document); // POST /mcp, Streamable HTTP, stateless
```

Nothing is mounted when no route is marked.

## How a tool is built

The tool's input schema comes from the route's OpenAPI operation:

- path and query parameters become top-level arguments
- the JSON request body becomes the `body` argument

`@McpTool` options:

| Option | Default |
|---|---|
| `name` | the route's OpenAPI `operationId` |
| `description` | the route's `@ApiOperation` summary |
| `destructive` | `true` for `DELETE` routes |

`GET` routes are marked read-only.

The app fails at startup when a marked route has an untyped body (`@Body() body: any`) or when two tools share a name. Type the body with a DTO class whose fields use `@ApiProperty`.

## Apso services

Services generated by `@apso/cli` already call `mountMcp`. Opt an entity's CRUD routes in from `.apsorc`:

```json
{ "name": "Invoice", "mcp": ["read", "create"] }
```

`"mcp": true` exposes read, create, update and delete. Add `@McpTool` to your own controllers the same way as above.

## OAuth sign-in for MCP clients

When your API takes OAuth access tokens from an identity provider (Auth0, Clerk and similar), tell `@apso/mcp` about it and MCP clients such as Claude can sign the user in themselves. Provide the settings under the `MCP_AUTH` token in any module:

```ts
import { MCP_AUTH, McpAuth } from '@apso/mcp';

{
  provide: MCP_AUTH,
  inject: [AuthGuard],
  useFactory: (guard: AuthGuard): McpAuth => ({
    authorizationServers: ['https://your-tenant.auth0.com/'],
    resource: process.env.MCP_RESOURCE_URL, // https://api.example.com/mcp
    verify: (req) => guard.authenticate(req), // the same check your API runs
  }),
}
```

With that in place:

- A request to `/mcp` without a valid token gets `401` with `WWW-Authenticate: Bearer resource_metadata="..."`. That response is what makes a client start sign-in.
- `/.well-known/oauth-protected-resource/mcp` (and the root form) serve the metadata that names your identity provider ([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)).
- Every request to `/mcp`, including listing tools, needs a valid token.

The server never issues tokens and never forwards them anywhere else. Your identity provider signs the user in, and your own token check decides whether a token is accepted. Check the token's audience in `verify`: the MCP specification requires a server to accept only tokens issued for it.

Set `resource` to the public URL of the endpoint. Without it the URL is built from the request's host, which is wrong behind a proxy that rewrites it.

Your identity provider has to support what MCP clients need to register themselves: Client ID Metadata Documents, or Dynamic Client Registration, or a client you registered by hand.

## Telling an MCP call from a REST call

A tool call reaches your route as an ordinary request. To tell the two apart, read `req.apso.mcp` in a handler, guard or interceptor:

```ts
import { McpOrigin } from '@apso/mcp';

const mcp: McpOrigin | undefined = req.apso?.mcp;
// { tool: 'approve_invoice', clientId: 'claude-web' } for a tool call, undefined for a REST call
```

`@apso/mcp` sets the property on the request object it builds in memory for the tool call. A REST caller can only send headers and a body, so it cannot set it.

`clientId` is the client application the caller's token was issued to. It is present when `McpAuth.verify` resolves to an object with a string `clientId`, for example `{ clientId: claims.azp }`.

`req.apso` is the property Apso libraries share. Your auth guard writes the caller to `req.apso.caller` and `@apso/logging` reads both, so set fields on it and do not replace the object:

```ts
req.apso = { ...req.apso, caller: { type: 'user', userId, tenantId } };
```

## Browser-based MCP clients (CORS)

An MCP client that runs in a browser on another origin needs the endpoint to answer its preflight request and to let it read the sign-in challenge.

- The allowed origins default to your app's own setting, the comma-separated `ALLOWED_ORIGINS` environment variable. With it unset, no browser origin is allowed.
- To allow other origins for MCP only, pass them: `mountMcp(app, document, { allowedOrigins: ['https://agent.example.com'] })`. `'*'` allows every origin.
- For an allowed origin the endpoint answers `OPTIONS`, allows the headers the preflight asks for, and exposes `WWW-Authenticate`, `Mcp-Session-Id`, `Mcp-Protocol-Version` and `X-Request-Id` to the page.
- A request with an `Origin` header that is not allowed gets `403`, as the MCP transport specification requires. Clients that are not browsers send no `Origin` header and are not affected.

`Access-Control-Allow-Credentials` is not set: browser MCP clients send the token in the `Authorization` header, not a cookie.

## Limits

- Without `MCP_AUTH`, listing tools is open, like the OpenAPI document it is built from. Calling a tool is always checked by the route's guards.
- Scopes are not checked yet: a signed-in user's agent can do what the user can.
- Express only.
